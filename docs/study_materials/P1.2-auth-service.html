P1.2 — auth-service: login, signup & JWKS

This stage builds the Identity Provider (IdP) — the one service that ever sees a password. It checks a password, looks up what the user is allowed to do, and mints a signed token that carries those permissions. If P1.1 made a token trustworthy, P1.2 is where a real person logs in and actually gets one. No prior auth experience needed — every idea is in plain English.

1 · The big idea

One service — and only one — checks passwords. When the password is right, it hands back a signed token that says who you are and what you may access.

This is the heart of the project's one rule: centralize authentication, keep authorization local. "Authentication" answers who are you? and happens in exactly one place: the IdP (our auth-service, port 8000). Every other service later trusts the token, never a password — most of the system never even sees one.

At login, the IdP does three things: (1) verify the password against a stored bcrypt hash; (2) look up the user's entitlements (which tenants they may enter); (3) mint a token (using the P1.1 signing key) that carries those entitlements inside it. The token is the user's portable proof — they present it to any tenant.

Analogy. Airport check-in. You show your passport once at a single desk (the IdP). They print a boarding pass (the token) listing your name and exactly which gates you may enter (entitlements). At each gate, staff just read the boarding pass — they never re-check your passport. Lose the desk and you can't fly; but once you hold the pass, the gates are quick.

2 · What we built / changed

A new service (the IdP) built with the factory pattern, plus the password primitive it needs and a Postgres-backed store.

The IdP routes & factory

  • app.ts — createApp(deps) wires the routes over injected dependencies (store, keys, issuer/audience). No globals → fast tests.
  • login.ts — POST /login: validate, one bcrypt compare, mint a token.
  • signup.ts — POST /signup: create an identity + grant the default entitlement.
  • jwks.ts — GET /.well-known/jwks.json: serve the public key over HTTP.

Supporting code, store & tests

  • password.ts — hashPassword / verifyPassword (bcrypt) + a precomputed DUMMY_HASH.
  • db/ + server.ts — PgAuthStore, idempotent schema.sql, seed (alice, bob), real wiring.
  • Tests: password (2) + login (5) + signup (3) + jwks (3) — 33/33 green (13 new + 20 from P1.1).
  • Decisions: ADR-0003, ADR-0006, ADR-0009.

3 · Must-know concepts (top 5)

The ideas to walk away with. Each card: definition → why it matters → analogy → the pitfall.

1The IdP is the only password checker

What it is

Authentication is centralized in one service. auth-service owns auth_db (identities + entitlements) and the private signing key. No other service stores or checks a password.

Why it matters

Passwords are the most dangerous secret in the system. Keeping them in one place means one place to harden, audit, and reason about — and adding a third, fourth, or tenth app needs no new password handling at all.

Analogy. A building with a single security desk at the entrance. You prove who you are once; every interior door just reads your badge.
Pitfall. Letting a second service "just also check passwords." Now there are two places to leak credentials and two login behaviours to keep consistent. Authentication must stay in exactly one service.

2Constant-time login (no user enumeration)

What it is

Enumeration = an attacker figuring out which emails are registered by watching how the server responds. We prevent it: wrong password and unknown email return the same body (401 invalid_credentials) in the same time.

Why it matters

If "unknown email" answered faster (because no hash check ran) or differently, an attacker could harvest a list of real accounts to target. We always run one bcrypt compare — against DUMMY_HASH when the email is unknown — so both paths cost the same.

Analogy. A doorman who takes exactly the same amount of time to turn everyone away, whether the name is on the list or not — so loiterers learn nothing from how long it took.
Pitfall. if (!user) return 401 before hashing. That early return is fast, and the timing gap silently leaks which emails exist. (ADR-0006)

3Entitlements are minted into the token at login

What it is

The IdP reads the user's grants (getEntitlements(sub)) and bakes them into the signed token as entitlements: { "tenant_a": ["member"], ... }. Authorization data travels inside the token.

Why it matters

Because the token is signed, the entitlements can't be tampered with — and tenants can authorize a request by reading the token, with no call back to the IdP. The IdP isn't a per-request bottleneck.

Analogy. The gates printed on your boarding pass. The gate agent reads the pass; they don't phone check-in to ask whether you're allowed.
Pitfall. Entitlements are only as fresh as the token. Revoke a grant and the old token still works until it expires — which is why tokens are short-lived (15 min). (ADR-0003)

4The factory pattern makes the IdP testable

What it is

createApp(deps) takes its dependencies — the data store, the signing keys, the issuer/audience — as arguments, instead of reaching for global state. Production builds them from Postgres + PEM files; tests pass an in-memory store and an ephemeral keypair.

Why it matters

The whole login/signup/JWKS surface can be tested in milliseconds with no Postgres and no Docker. Tests stay fast, isolated, and deterministic.

Analogy. An appliance with a power plug instead of a hard-wired cable. In the lab you plug it into a test bench; at home it plugs into the wall. Same appliance, swappable source.
Pitfall. Importing a global DB connection inside route code. Then a test can't run without a real database, and two tests can pollute each other's data.

5Signup creates an identity and a default grant — but no token

What it is

POST /signup makes the central identity, hashes the password, and grants the default entitlement tenant_a:[member]. It returns { sub, email } — the user logs in separately to get a token.

Why it matters

A brand-new user is now entitled to tenant_a but has no local account row in that tenant yet. That exact state — "allowed in, but not provisioned here" — is the setup for Flow C (just-in-time provisioning) in P1.4.

Analogy. Being added to the company directory and granted building access, before HR has created your desk and locker in a specific office. You may enter; your local spot gets made on first arrival.
Pitfall. This auto-grant is a study-MVP convenience, not production practice — real systems gate entitlement behind an admin/approval step. (ADR-0009)

4 · How it works (the code, gently)

Three short handlers carry the whole stage. Each starts by validating its input with zod at the very edge, before any database or crypto work.

Login — constant-time check, then mint

const identity = await store.findIdentityByEmail(email);            // may be null
// ★ Always run ONE bcrypt compare. Unknown email → compare vs DUMMY_HASH,
//   so the request still spends hash time. No timing leak (ADR-0006).
const ok = await verifyPassword(password, identity?.passwordHash ?? DUMMY_HASH);
if (!identity || !ok) return res.status(401).json({ error: "invalid_credentials" });

const entitlements = await store.getEntitlements(identity.sub);     // { tenant_a:[...], ... }
const access_token = await mint(keySet, { sub, email, entitlements, issuer, audience });
return res.json({ access_token, token_type: "Bearer", expires_in: 900 });

Wrong password and unknown email reach the same line and return the same 401 body. On success the token carries the entitlements, signed.

Signup — no duplicates, hash, grant the default

if (await store.findIdentityByEmail(email)) return res.status(409).json({ error: "email_taken" });
const sub = newSub();                                // e.g. "u_" + uuid (injectable for tests)
const passwordHash = await hashPassword(password);   // bcrypt, cost 12
await store.createIdentity({ sub, email, passwordHash, name });
await store.grantEntitlement(sub, "tenant_a", ["member"]);  // default grant (ADR-0009)
return res.status(201).json({ sub, email });         // no token — log in separately

Email is lowercased first, so ALICE@… and alice@… are the same account (the 409 check is case-insensitive).

JWKS — publish the public key over HTTP

const jwks = await buildJwks(keySet);                // public half only: { kty, n, e, kid, alg, use }
res.set("Cache-Control", "public, max-age=300");     // tenants may cache for 5 minutes
return res.status(200).json(jwks);

This is the HTTP front for the P1.1 buildJwks(). Tenants fetch it once, cache it, and verify tokens offline (wired up in P1.3). Private fields are never included.

A login request, end to end

1
Client → POST /login { email, password }. Malformed body → 400 before any work.
2
IdP checks the password → one bcrypt compare. Fail → 401 (identical for wrong-pw and unknown-email).
3
IdP looks up entitlements → { tenant_a:["member"], tenant_b:["member"] } for bob.
4
IdP mints & returns → 200 with { access_token, token_type:"Bearer", expires_in:900 }. The token's payload carries those entitlements, signed.

5 · Why each decision exists

Each choice answers a real "what if?".

DecisionThe worry it answers / the trade-off
Only the IdP checks passwords"Where do credentials live?" → one hardened service; tenants never see a password, so adding apps adds no password surface.
Always run one bcrypt compare (DUMMY_HASH)"What if unknown emails answer faster?" → they don't; both failure paths cost the same time and return the same body.
Identical 401 invalid_credentials"What can the error tell an attacker?" → nothing about whether the email exists or which half was wrong.
Entitlements minted into the token"How do tenants authorize without calling us every request?" → they read the signed token; the IdP isn't a bottleneck (15-min freshness trade-off).
createApp(deps) factory"How do we test the IdP fast?" → inject an in-memory store + ephemeral keypair; no Docker, milliseconds per test.
Signup grants a default, issues no token"How do we get an entitled-but-unprovisioned user for Flow C?" → signup does exactly that; login is a separate step.

6 · Technical decisions (ADRs)

The Architecture Decision Records this stage implements.

ADRDecisionWhy (plain)
0003 Carry entitlements inside the token The IdP decides grants once at login; tenants read them from the signed token and authorize offline.
0006 Constant-time login Wrong password and unknown email return the same body in the same time — no account harvesting.
0009 Signup grants tenant_a:[member] Produces an entitled-but-unprovisioned user — the precondition for Flow C (P1.4).

7 · How to test / check it locally

npm install
npm test                 # vitest — 33/33 (common + auth-service)
npm test -- login        # run just the /login criteria

A green run proves every acceptance criterion in spec 02: valid login returns a verifiable token carrying the right entitlements; wrong password and unknown email are byte-identical 401s and the unknown-email path still hashes; signup creates the identity + default grant, rejects duplicates with 409, and rejects short passwords with 400; and the JWKS endpoint serves a public-only key that verifies a minted token.

See it for real (needs Docker): 
docker compose up -d                                   # Postgres + auth_db (seeds on first boot)
AUTH_DATABASE_URL=postgres://sso:sso@localhost:5432/auth_db \
  npx tsx packages/auth-service/src/server.ts &
curl -s localhost:8000/.well-known/jwks.json           # public key + kid, no private fields
curl -s -X POST localhost:8000/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"bob@example.com","password":"password123"}'   # → access_token; decode it
Decode the token's middle part (base64url) to see entitlements, iss, aud, sub, and exp − iat = 900.

8 · Glossary (new terms this stage)

IdP (Identity Provider)
The one service that authenticates users and mints tokens. Here, auth-service on :8000.
Authentication vs authorization
Authentication = "who are you?" (the IdP). Authorization = "what may you do here?" (each tenant).
bcrypt
A deliberately slow password-hashing function. Slowness makes brute-forcing a stolen hash expensive.
Hash (password)
A one-way scramble of a password stored instead of the password itself, so a DB leak doesn't reveal plaintext.
Cost factor / rounds
bcrypt's work setting (here 12 → 2¹² iterations). Higher = slower = harder to crack.
DUMMY_HASH
A real bcrypt hash no password matches, compared against on unknown-email logins to keep timing constant.
User enumeration
An attack that discovers which emails are registered by observing response differences (body or timing).
Entitlement
A grant of access to a tenant, e.g. tenant_a:["member"]. Decided by the IdP, carried in the token.
Identity (sub)
A user's global account at the IdP. sub (subject) is its stable id, e.g. u_bob.
Factory pattern
createApp(deps) — building the app from injected dependencies instead of globals, so tests swap them out.
Dependency injection
Passing collaborators (store, keys) in as arguments rather than importing fixed ones inside.
zod
A schema-validation library used to check request bodies at the edge of each route.
Provisioning (preview)
Creating a user's local row inside a tenant. A signed-up user is entitled but not yet provisioned (Flow C, P1.4).
Bearer token
A token whose mere possession grants access; sent later as Authorization: Bearer <token>.

9 · Self-quiz

Answer from memory before expanding.

1. Why does the login route hash a password even when the email is unknown?

To keep timing constant. It compares against DUMMY_HASH so unknown-email and wrong-password take the same time and return the same body — no user enumeration. (ADR-0006)

2. Where do a token's entitlements come from, and why put them in the token?

The IdP reads them from auth_db at login and signs them into the token. Tenants then authorize by reading the signed token — no per-request call back to the IdP. (ADR-0003)

3. What does POST /signup return, and what state is the new user in?

201 { sub, email } — no token. The user is entitled to tenant_a but has no local row there yet: the Flow C precondition. (ADR-0009)

4. Why does createApp take its store and keys as arguments?

So tests inject an in-memory store and an ephemeral keypair and run with no Postgres or Docker — fast, isolated, deterministic. That's the factory pattern.

5. A wrong password returns 401 invalid_credentials. What does an unknown email return?

Exactly the same — byte-identical 401 invalid_credentials, in the same time. The attacker can't tell the two cases apart.

6. What's the difference between authentication and authorization, and which does P1.2 do?

Authentication = "who are you?"; authorization = "what may you do here?". P1.2 (the IdP) does authentication and records authorization as entitlements in the token. Enforcing them happens at the tenant in P1.3.
