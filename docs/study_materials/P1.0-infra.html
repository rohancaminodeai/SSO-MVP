1 · The big idea

In one sentence: define every security-critical constant and every environment value once, in a single validated file, so nothing else in the codebase can hardcode or guess them.

A Single Sign-On (SSO) system stands or falls on a few values being exactly right everywhere: which signing algorithm we trust, how long a token lives, who the token is for. If those values were copied around the code, one wrong copy would be a security hole. P1.0 puts them in packages/common/src/config.ts and adds a small loader that refuses to start if the environment is misconfigured.

Analogy — the festival's rulebook. Before a music festival opens, staff agree on one rulebook: what a real wristband looks like, how long it is valid, which gate prints them. Every guard works from that one rulebook. If each guard invented their own rules, fakes would slip through. config.ts is that single rulebook for our tokens.

3 · Must-know concepts (top 5)

The ideas to walk away with as an intermediate→senior engineer. Each card: what it is → why it matters → analogy → the pitfall.

1Asymmetric signing (RS256) + algorithm pinning

What it is

Symmetric (HS256): one shared secret both signs and verifies — anyone who can verify can also forge. Asymmetric (RS256): a private key signs, a separate public key only verifies. The IdP (Identity Provider) keeps the private key; tenants get the public key only. "Pinning" means verification accepts RS256 and nothing else.

Why it matters

It means a hacked tenant can check tokens but never forge them — the power to mint tokens stays in exactly one place.

Analogy — a wax seal. Only the king's ring (private key) can stamp the letter; anyone with a picture of the seal (public key) can confirm it is real, but cannot make their own.
Pitfall. A forged token sets its header to "alg":"none" ("no signature, trust me") or HS256 (tricking the server into using the public key as a shared password). Always verify with algorithms:["RS256"] — never trust the algorithm written inside the token. (ADR-0001, ADR-0002)

2Centralize authentication, keep authorization local

What it is

Authentication = "Who are you?" — happens in one place (the IdP), the only service that ever sees a password. Authorization = "What may you do here?" — each tenant decides for itself using its own data.

Why it matters

This split is the whole idea of SSO: log in once, then each app independently decides access. One place to secure passwords; many places that simply trust a signed token.

Analogy — an office keycard. You badge in once at the front desk (authentication). After that, each door decides on its own whether your card opens it (authorization).
Pitfall. Letting a tenant re-check passwords, or letting the IdP decide per-tenant permissions, collapses the separation and spreads credentials everywhere.

3The 401 vs 403 taxonomy

What it is

401 = "I don't know who you are" (authentication failed — missing, bad, or expired token). 403 = "I know who you are, but you can't be here" (authorization failed — you lack the entitlement).

Why it matters

The status code is a contract. Mixing them up confuses clients and hides real bugs. The first failing check decides the code.

StatusMeaningExample
401UnauthenticatedNo Authorization header; expired token.
403UnauthorizedValid token, but its entitlements don't name this tenant.

4Config as a security control + fail-fast validation

What it is

Token lifetime, clock leeway, and the algorithm are not "settings" — they are security decisions. They live pinned in one validated file, and loadConfig() uses zod to reject a malformed ISSUER URL or an unknown TENANT_ID at boot.

Why it matters

A misconfigured service crashes immediately with a clear error, instead of running and silently minting or accepting bad tokens in production.

Analogy — a preflight checklist. The plane refuses to leave the gate if a critical switch is wrong, rather than discovering it mid-air.
Pitfall. Reading process.env ad-hoc across the codebase with no validation lets a typo (tenant_zz) survive until a confusing runtime failure far from its cause.

5Dependency injection / the factory pattern

What it is

loadConfig(env, options) receives its environment as an argument instead of reaching out to a global. The same shape scales to whole services later: createApp(deps) takes its database and keys as arguments.

Why it matters

Injected dependencies make code testable: a test passes a fake env (or a throwaway database and an ephemeral keypair) and exercises the real logic in milliseconds, no Docker needed.

Analogy — a coffee machine with a water inlet. You can plug in tap water or a test bottle. A machine welded to the city pipe can only be tested by flooding the building.
Pitfall. Hardcoding process.env / real DB connections deep inside functions makes them nearly impossible to unit-test.

4 · How it works (the code, gently)

The two pieces that matter: the pinned constants, and the loader that validates the environment.

The pinned constants — the single source of truth

// packages/common/src/config.ts — no other file may hardcode these.
export const ALG = "RS256";                  // signing algorithm (asymmetric)
export const ACCESS_TOKEN_TTL_SECONDS = 900; // tokens live 15 minutes
export const CLOCK_LEEWAY_SECONDS = 60;      // tolerate ±60s clock difference
export const TENANT_IDS = ["tenant_a", "tenant_b"]; // the tenants we know

Short token life limits the damage if a token is stolen; the leeway absorbs small clock differences between the IdP and the tenants.

The env loader — read, validate, fail fast

const envSchema = z.object({
  ISSUER:    z.string().url().default(ISSUER_DEFAULT),   // must be a URL
  AUDIENCE:  z.string().min(1).default(AUDIENCE_DEFAULT),
  TENANT_ID: z.enum(TENANT_IDS).optional(),              // only known tenants
});

export function loadConfig(env = process.env, options = {}) {
  const parsed = envSchema.parse(env);   // ⚠ throws on a bad ISSUER / unknown TENANT_ID
  const dbUrlKey = options.dbUrlKey ?? "AUTH_DATABASE_URL"; // each service picks its DB
  return { issuer: parsed.ISSUER, audience: parsed.AUDIENCE,
           databaseUrl: env[dbUrlKey], tenantId: parsed.TENANT_ID };
}

A tenant-service instance calls loadConfig(process.env, {dbUrlKey: "TENANT_B_DATABASE_URL"}) — same loader, different database. That options argument is the factory pattern in miniature.

5 · Why each decision exists

Each choice answers a real-world "what if?".

DecisionThe worry it answers / the trade-off
One pinned config file"What if a constant is wrong in one place?" → There is only one place, so it can't drift.
Pin alg to RS256"What if an attacker changes the token's algorithm?" → We accept only RS256, killing alg:none / HS256 confusion.
Short 15-min token TTL"What if a token is stolen?" → It expires fast, shrinking the damage window. Trade-off: more frequent re-issuing.
±60s clock leeway"What if two servers' clocks differ slightly?" → Tolerate 60s so valid tokens aren't wrongly rejected.
Fail-fast env validation"What if the environment is misconfigured?" → Crash loudly at boot instead of misbehaving later.
loadConfig(env) takes an argument"How do we test config without real env?" → Inject a fake env; test in milliseconds.

6 · Technical decisions (ADRs)

The Architecture Decision Records this stage sets up. (An ADR is a short note: "we decided X, because Y, trade-off Z.")

ADRDecisionWhy (plain)
0001RS256 asymmetric signingPrivate key signs at the IdP; tenants verify with the public key.
0002Pin the algorithm to RS256Defeats alg:none / HS256 key-confusion forgery.
0003Entitlements inside the tokenTenants learn permissions from the token, no extra IdP lookup.

7 · How to test / check it locally

npm install
npm test                 # vitest — pinned constants + env loader (the P1.0 gate)
npx tsc --noEmit         # type-check passes, no build errors
docker compose up -d     # starts Postgres with the 3 databases

A green run proves the spec's acceptance criteria: the constants are exactly RS256 / 900 / 60; defaults load when no env is set; provided values parse correctly; and a bad ISSUER URL or unknown TENANT_ID throws.

8 · Glossary (new terms this stage)

IdP (Identity Provider)
The central login server; the only service that checks passwords and signs tokens.
Tenant
One app/workspace with its own database. Trusts signed tokens; never checks passwords.
JWT (JSON Web Token)
A small signed token carrying facts ("claims") about the user.
RS256
Asymmetric signing: a private key signs, a public key verifies.
JWKS (JSON Web Key Set)
A public page listing the IdP's public keys so tenants can verify offline.
Entitlement
A grant saying "this identity may access this tenant."
Clock leeway
Allowed time difference (here ±60s) when checking token expiry across machines.
TTL (time to live)
How long a token stays valid (here 900 seconds = 15 minutes).
Factory pattern
Building a thing via a function that takes its dependencies as arguments, so tests can swap them.
zod
A TypeScript library that validates data against a schema and throws on bad input.

9 · Self-quiz

Answer from memory before expanding. If you can do these, you understand P1.0.

1. Why does a tenant get the public key but never the private key?

So a compromised tenant can verify tokens but never forge them. The power to mint tokens stays solely at the IdP. That is the point of RS256.

2. What attack does algorithms:["RS256"] stop, and how?

It rejects tokens that set alg:none (no signature) or HS256 (key-confusion, using the public key as a shared secret). By accepting only RS256, both are dead on arrival.

3. Give one example each of a 401 case and a 403 case.

401: no Authorization header, or an expired/forged token. 403: a valid token whose entitlements don't name this tenant.

4. Why is it better for a service to crash at boot on bad config?

A loud, immediate failure points straight at the misconfiguration. A service that keeps running might silently mint or accept bad tokens, surfacing as a confusing failure later, far from the cause.

5. Why does loadConfig take env as a parameter instead of reading globals?

So tests can inject a fake environment and exercise the real logic in milliseconds. It is the same dependency-injection shape that whole services use later via createApp(deps).
