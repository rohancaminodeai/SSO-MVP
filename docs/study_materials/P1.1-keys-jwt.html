P1.1 — Keys, JWT & alg Pinning

This stage builds the part of the system that makes a token trustworthy: a signing key at the Identity Provider, a way to mint (create & sign) a token, and a safe way for anyone else to verify it. If you understand this stage, you understand why an SSO token can't be faked. No cryptography background needed — we explain each idea in plain English.

1 · The big idea

The Identity Provider signs a token with a private key only it has; everyone else verifies that token with a matching public key — and we verify in a way that can't be tricked.

A token is just a small piece of text that says "this is Alice, and she may enter Tenant A". On its own, text is worthless — anyone could type the same thing. What makes it trustworthy is a digital signature: a mathematical seal that proves who created the token and that nobody changed it afterwards.

We use RS256 (an asymmetric algorithm): there are two keys, not one. A secret private key creates the seal; a freely-shared public key checks it. Only the holder of the private key (the IdP) can make a valid token; anyone with the public key can confirm it's real, but can never make their own.

Analogy. A wax seal on a royal letter. Only the king's ring (the private key) can press a genuine seal. Anyone who has seen the seal (the public key) can recognise a real one — but they can't forge it, because they don't have the ring.

2 · What we built / changed

Two small, security-critical files in the shared library, plus their tests.

Code & tests

3 · Must-know concepts (top 4)

The ideas to walk away with. Each card: definition → why it matters → analogy → the pitfall.

1Asymmetric signing (RS256)

What it is

A signing scheme with two keys: a secret private key that creates signatures, and a public key that only verifies them. "RS256" = RSA signatures with SHA-256 hashing.

Why it matters

The power to create tokens stays in exactly one place (the IdP). Every other service can check tokens but can never mint them — so one hacked tenant can't forge logins for the others.

Analogy. A tamper-proof rubber stamp. Only head office owns the stamp (private key); branch offices can recognise a stamped document (public key) but can't stamp their own.
Pitfall. Using a symmetric scheme (one shared secret, e.g. HS256) instead. Then every verifier also holds the power to forge — one leak compromises everyone. (ADR-0001)

2alg pinning

What it is

When verifying, we tell the library exactly which algorithm to accept: algorithms: ["RS256"]. We never let the token's own header decide how it's checked.

Why it matters

The two most famous JWT attacks both come from trusting the token's alg field. Pinning makes both impossible — the verifier simply refuses anything that isn't an RS256 signature.

Analogy. A bouncer who only accepts one specific kind of ID and ignores whatever the card claims it is. A homemade card that says "trust me, no check needed" gets turned away at the door.
Pitfall. Two classic forgeries: alg:none (attacker sets algorithm to "none" and removes the signature) and HS256 confusion (attacker signs with HS256 using the public key as the secret). Both succeed if you don't pin. (ADR-0002)

3JWKS and the kid

What it is

JWKS (JSON Web Key Set) is a small public document listing the IdP's public keys. Each key has a kid (key id). The token's header names a kid so a verifier knows which public key to use.

Why it matters

It lets tenants verify offline (no call back to the IdP) and lets the IdP rotate keys later: publish a new key with a new kid, and old + new tokens both verify.

Analogy. A public noticeboard of official signatures. Anyone can copy the noticeboard to check a document, but copying a signature sample doesn't let you sign for the office. The kid is the little reference number next to each sample.
Pitfall. Accidentally publishing the private parts of the key (d, p, q…) in the JWKS. That hands attackers the power to forge. Our buildJwks() exports the public half only — and a test asserts the private fields are absent.

4Short lifetime + clock leeway

What it is

Each token carries an expiry (exp) 15 minutes out. Verifiers allow ±60 seconds of leeway for clock differences between machines.

Why it matters

A short life limits the damage if a token is stolen. The small leeway prevents honest tokens from being rejected just because two servers' clocks differ by a few seconds.

Analogy. A concert wristband that's only valid for tonight (short life), and a door staff who won't quibble over a one-minute clock difference (leeway).
Pitfall. Zero leeway → random "token expired" failures across servers. Too much leeway → expired tokens linger. 60s is the sweet spot for this MVP.

4 · How it works (the code, gently)

Three short snippets carry the whole stage.

Minting a token (IdP only)

return new SignJWT({ email, entitlements })          // custom claims (who + what they may access)
  .setProtectedHeader({ alg: "RS256", kid: keySet.kid }) // pin the alg; name which key
  .setIssuer(issuer).setAudience(audience)               // iss = the IdP, aud = the tenants
  .setSubject(sub).setIssuedAt(iat)
  .setExpirationTime(iat + 900)                          // 15-minute life
  .sign(keySet.privateKey);                              // the seal — private key only

Only the IdP holds privateKey, so only the IdP can produce a token that will verify.

Verifying a token (everyone else) — the safe part

const { payload } = await jwtVerify(token, publicKey, {
  algorithms: ["RS256"],          // ★ the pin — rejects alg:none and HS256 confusion
  issuer, audience,               // must be OUR issuer and audience
  clockTolerance: 60,             // ±60s leeway; also enforces exp
});

This single call checks the signature, the algorithm, the expiry, and the issuer/audience. If anything is wrong it throws — later stages turn that throw into a 401.

Publishing the public key (JWKS)

const jwk = await exportJWK(keySet.publicKey);          // public half only → { kty, n, e }
return { keys: [{ ...jwk, kid: keySet.kid, alg: "RS256", use: "sig" }] };

The private fields are never exported here. The kid is an RFC 7638 thumbprint (a fingerprint of the public key), so it's stable and unique.

What a real token looks like (decoded)

1
Header → { "alg": "RS256", "kid": "xc72x-…" } — how it's signed + which key.
2
Payload → { email, entitlements:{tenant_a:["member"]}, iss, aud, sub, iat, exp } — the facts, with exp − iat = 900 seconds.
3
Signature → the RS256 seal over header + payload. Change one character above and the signature no longer matches.

5 · Why each decision exists

Each choice answers a real "what if?".

DecisionThe worry it answers / the trade-off
RS256 (asymmetric), not HS256"What if a tenant is hacked?" → it only has the public key, so it can verify but never forge tokens for other tenants.
Pin algorithms:["RS256"]"What if an attacker edits the alg header?" → ignored; alg:none and HS256-confusion are rejected.
kid = public-key thumbprint"How do verifiers pick the right key, and how do we rotate keys later?" → a stable id in the header selects the key.
15-min expiry + 60s leeway"What if a token is stolen / clocks drift?" → short life caps the damage; small leeway avoids false rejections.
Throw on any failure"How should callers react?" → one clear failure path that the service layer maps to 401 — no partial trust.

6 · Technical decisions (ADRs)

The Architecture Decision Records this stage implements.

ADRDecisionWhy (plain)
0001 RS256 asymmetric signing Private key signs at the IdP; tenants verify with the public key and can't forge.
0002 Pin the verification algorithm to RS256 Kills the alg:none and RS256→HS256 key-confusion forgeries.

7 · How to test / check it locally

npm install
npm test                 # vitest — 20/20 (config + keys + jwt)
npm test -- jwt          # run just the JWT criteria

A green run proves every acceptance criterion in spec 01: a minted token verifies and returns its claims; a tampered token, an alg:none token, and an HS256 token are all rejected; an expired token fails while one inside the 60s leeway still passes; and the wrong iss or aud is rejected. The JWKS test proves no private fields leak.

Want to see a token by eye? Mint one and base64url-decode the first two dot-parts — the header shows alg:RS256 + kid, the payload shows the claims.

8 · Glossary (new terms this stage)

JWT (JSON Web Token)
A signed token of three dot-separated parts: header, payload, signature.
Claim
A single fact inside the payload, e.g. sub, email, entitlements.
Mint
To create and sign a token. Only the IdP mints.
RS256
RSA signature + SHA-256 hash. Asymmetric: private key signs, public key verifies.
Asymmetric / symmetric
Asymmetric = two different keys (sign vs verify). Symmetric = one shared secret for both.
Private key / public key
The secret signer (IdP only) and the freely-shared verifier.
alg pinning
Telling the verifier the exact algorithm to accept, ignoring the token's own header.
alg:none
An attack token claiming "no signature"; rejected by pinning.
HS256 confusion
An attack that signs with HS256 using the public key as the secret; rejected by pinning.
JWKS (JSON Web Key Set)
A public document listing the IdP's public keys for verifiers.
kid (key id)
An identifier (here an RFC 7638 thumbprint) naming which key signed a token.
Thumbprint
A stable fingerprint computed from a key's public fields.
iss / aud
Issuer (who made the token) and audience (who it's for).
exp / iat
Expiry time and issued-at time (Unix seconds).
Clock leeway
Allowed clock-skew tolerance (±60s) when checking time-based claims.

9 · Self-quiz

Answer from memory before expanding.

1. Which key signs a token, and which key verifies it?

The private key (held only by the IdP) signs; the public key verifies. Public can check but never forge.

2. Name the two attacks that alg pinning prevents.

alg:none (strip the signature) and HS256 confusion (sign with HS256 using the public key as the HMAC secret). Pinning ["RS256"] rejects both.

3. What is the kid for?

It names which public key signed the token, so a verifier picks the right one from the JWKS — and it enables key rotation.

4. Why must the JWKS never contain d, p, or q?

Those are private key fields. Publishing them hands attackers the power to forge tokens. JWKS is public — public fields only (n, e).

5. A token expired 30 seconds ago still verifies. Bug or correct?

Correct — it's within the ±60s clock leeway. A token expired 120s ago is rejected.

6. verify() throws. What HTTP status will the service return later, and why?

401 — authentication failed: the token is missing/invalid/expired, i.e. "I don't know who you are." (403 is for "I know you, but you can't be here," which comes later from the entitlement check.)
