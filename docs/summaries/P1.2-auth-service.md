## The feature

The **Identity Provider (IdP)** — the one place a password is ever checked. It authenticates a user,
looks up their entitlements, and mints a signed token that carries those entitlements so tenants can
authorize offline later. Signup creates the central identity; JWKS publishes the public key.

## Why it matters

- **"Centralize authentication."** Passwords live in exactly one service. Every other service trusts
  the signed token, never a password.
- **No user enumeration.** Wrong password and unknown email return the *same body* in the *same time*
  (one bcrypt compare always runs), so an attacker can't probe which emails are registered (ADR-0006).
- **Authorization rides inside the token.** The IdP decides entitlements once, at login; the signature
  makes them tamper-proof; tenants read them without calling back (ADR-0003).

## How to test locally

```bash
npm install
npm test                       # vitest — 33/33

# Manual proof (needs Docker):
docker compose up -d           # Postgres + auth_db (seeds run on first boot)
AUTH_DATABASE_URL=postgres://sso:sso@localhost:5432/auth_db \
  npx tsx packages/auth-service/src/server.ts &
curl -s localhost:8000/.well-known/jwks.json                 # public key only, has kid
curl -s -X POST localhost:8000/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"bob@example.com","password":"password123"}'   # → access_token (decode it)
curl -s -X POST localhost:8000/login \
  -d '{"email":"ghost@example.com","password":"x"}'            # 401, identical to wrong-password
```

## Top 5 must-know concepts

1. **The IdP is the only password checker.** Authentication is centralized; authorization stays local.
   `auth-service` owns `auth_db` (identities + entitlements) and the private signing key.
2. **Constant-time login (no enumeration).** Always run one bcrypt compare — on unknown email, compare
   against `DUMMY_HASH` — and return an identical `401 invalid_credentials`. Differences in body or
   *timing* leak which emails exist. (ADR-0006)
3. **Entitlements are minted into the token at login.** `login` reads `getEntitlements(sub)` and bakes
   `{ "tenant_a": ["member"], ... }` into the signed JWT. Tenants trust the signature, not a callback. (ADR-0003)
4. **Factory pattern = testable IdP.** `createApp(deps)` takes its store + keys as arguments, so tests
   inject an in-memory store and an ephemeral keypair and run in milliseconds with no Postgres.
5. **Signup grants a default entitlement, issues no token.** New users get `tenant_a:[member]` but no
   local tenant row yet — the precondition for Flow C / JIT provisioning in P1.4. (ADR-0009)

## Technical decisions (ADRs)

| ADR | Decision | Why |
|---|---|---|
| [0003](../adr/0003-entitlements-in-token.md) | Carry entitlements inside the token | IdP decides once at login; tenants authorize offline. |
| [0006](../adr/0006-no-user-enumeration.md) | Constant-time login | Same body + same time for wrong-pw and unknown-email. |
| [0009](../adr/0009-signup-default-entitlement.md) | Signup grants `tenant_a:[member]` | Produces an entitled-but-unprovisioned user for Flow C. |
