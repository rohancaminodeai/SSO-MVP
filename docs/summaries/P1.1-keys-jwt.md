## The feature

The **cryptographic core** the whole trust model rests on: the IdP can sign a token with its private
key, anyone can verify it with the public key, and verification is *safe by construction* — it pins
RS256 so forged tokens (`alg:none`, RS256→HS256 confusion) are rejected.

## Why it matters

- **Signing is what makes a token trustworthy.** Without a verifiable signature, a "token" is just a
  claim anyone could fake. RS256 means only the IdP (private key) can mint; everyone else (public
  key) can only check.
- **Pinning is the difference between secure and forgeable.** The two most famous JWT attacks both
  come from trusting the token's own `alg` header; pinning `["RS256"]` kills both.
- **JWKS hides the secret.** Publishing only the public half lets tenants verify offline without ever
  holding the power to sign.

## Top 4 must-know concepts

1. **Asymmetric signing (RS256).** Private key signs at the IdP; public key verifies everywhere. A
   leaked public key can verify but never forge. (ADR-0001)
2. **`alg` pinning.** Always verify with `algorithms:["RS256"]`. Trusting the token's `alg` header
   enables `alg:none` (strip the signature) and HS256 key-confusion (sign with the public key as an
   HMAC secret). (ADR-0002)
3. **JWKS + `kid`.** The public key is published at a well-known JSON endpoint; the `kid` (key id, an
   RFC 7638 thumbprint) tells verifiers which key to use and makes rotation possible. Never publish
   private fields (`d`/`p`/`q`/…).
4. **Short life + clock leeway.** Tokens expire in 15 minutes (limits theft); verification tolerates
   ±60s of clock skew so honest tokens aren't rejected over a tiny time difference.
